# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

> ร่างการเปรียบเทียบโดย AI จาก [Run a](outputs/2a-adr.md), [Run b](outputs/2b-adr.md), `docs/scenario.md` และ `system/online-boutique/src/checkoutservice/main.go`; ให้นิสิตตรวจและปรับความเห็นก่อนส่ง

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ใช้ เพราะ context เป็น none; ระบุ latency, ปริมาณงาน, SLA และข้อจำกัด MailFast เป็น Open questions ตามหลักฐานที่ได้รับ | ใช้ p95 checkout ≤ 500 ms (ปัจจุบันประมาณ 300 ms), ช่วงพีก 200 คำสั่งซื้อ/วินาที, MailFast p95 1.5 s / p99 8 s / ล้มเหลวประมาณ 0.5% / จำกัด 50 อีเมล/วินาที และแต้มภายใน 1 นาที ตรงกับ `docs/scenario.md:24–28` |
| ทางเลือกที่พิจารณา (ระบุ) | 2 ทางเลือก: เรียกบริการแบบ synchronous และเผยแพร่ event แบบ asynchronous ผ่าน broker; เลือกแนวทาง event แต่ยังไม่เลือกผลิตภัณฑ์ | 3 ทางเลือกในไฟล์ 2b ปัจจุบัน: เรียกตรง, PostgreSQL job store พร้อม worker/retry แยกตาม action และ PostgreSQL outbox + RabbitMQ; เลือกทางเลือก 3 เพราะรองรับ action เพิ่มและทีมบางส่วนมีประสบการณ์ RabbitMQ โดยยังต้องเทียบภาระดูแลกับทางเลือก 2 |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | เสนอป้องกันผลซ้ำด้วยสถานะถาวรตาม order_id กับชนิดงาน และบันทึกคะแนนกับสถานะกันซ้ำให้สอดคล้องกัน; ถาม rate limit และ idempotency ของ MailFast ใน Open questions จึงยังไม่มีอัตราส่งที่กำหนด | เสนอ durable ledger มี unique key ตาม order_id กับชนิดการให้แต้ม และบันทึกการกันซ้ำกับเพิ่มแต้มใน transaction เดียวก่อน ACK; แยกคิวแต้มจากอีเมล และจำกัด MailFast รวมทุก replica และ retry ≤ 50 อีเมล/วินาที; ระบุว่าบริการแต้มล่มเกิน 1 นาทีทำให้รับประกัน SLA นี้กับ checkout สำเร็จเสมอพร้อมกันไม่ได้ |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่พบการอ้างตัวเลขหรือเครื่องมือเฉพาะว่าเป็นข้อเท็จจริงเดิม; outbox, event contract และการกันซ้ำระบุเป็นข้อเสนอ [Inferred] พร้อมคำถามค้าง | ไฟล์ 2b ปัจจุบันเลือก PostgreSQL เพิ่มในฐานะข้อเสนอ ไม่ใช่ระบบเดิม; มีงบเวลา 5/45/10 s และตัวอย่างพีค 10 นาที/หลังพีค 20 ครั้งต่อวินาทีที่ติดป้าย Assumption ซึ่งโจทย์ไม่ได้ให้ ตัวเลข 150 รายการ/วินาทีอนุมานจาก 200 − 50 ภายใต้หนึ่งอีเมลต่อ order; ไม่มีผลทดสอบจริง ฉบับปรับปรุงใน docs/adr ตัดตัวเลขตัวอย่างเหล่านี้และเก็บข้อมูลที่ยังไม่ทราบไว้ใน Open questions |

ข้อสังเกตจาก AI: ทั้งสอง run เสนอ asynchronous แต่บริบททำให้เหตุผลและเงื่อนไขตรวจรับชัดขึ้น ไฟล์ 2b ถูกปรับเพิ่มหลัง run แรก ตารางนี้สะท้อนฉบับปัจจุบัน จึงไม่ควรอ้างว่าเป็นการทดลองที่ควบคุมการแก้ไขทั้งสองฝั่งเท่ากัน ข้อเสนอปัจจุบันเลือก PostgreSQL แล้ว แต่ API ภายนอก recovery, ข้อยกเว้น SLA, ความจุ และผู้ดูแลยังไม่ยืนยัน ไม่มีผลทดสอบ implementation

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | แยกสถานะยังไม่ได้ประชุมออกจากข้อเสนอเทคนิค และคง Proposed ใน ADR ฉบับปรับปรุง | ป้องกันการอ่าน Recommendation ว่าเป็นมติหรือการลงชื่อรับรองแล้ว |
| 2 | ตัดงบเวลา 5/45/10 s และตัวอย่างพีค 10 นาที/อัตราหลังพีค 20 ครั้งต่อวินาทีจากฉบับปรับปรุง ใช้ SLA และสูตรความจุแทน | ตัวเลขเหล่านี้ไม่มีในโจทย์ ต้องรอธุรกิจยืนยัน ไม่ใช้ค่าตัวอย่างเป็นขนาด production |
| 3 | สรุป recovery และ validation เป็นตาราง พร้อมแยก request ซ้ำกับ event ซ้ำ และคง API/ผู้รับผิดชอบที่ยังไม่ทราบเป็นคำถามเปิด | ทำให้ตรวจรับได้ และไม่อ้างว่า outbox ทำให้ payment/shipping เป็น transaction เดียวกัน |

> **สถานะล่าสุด:** ผู้ใช้ยืนยันวันที่ 2026-10-27, ชวภณเป็น AI analyst, Product owner และ SRE โดยรับบททั้งสามเอง และณัฐเมธีเป็นสถาปนิกแล้ว หลังเห็นรีวิวในแชตใหม่ผู้ใช้ยืนยันคง Option 3 พร้อมเงื่อนไขสามข้อก่อนใช้งานจริง ตารางเปรียบเทียบตรวจจากไฟล์จริงโดย AI; บทบาท PO/SRE ยืนยันแล้วตามคำตอบล่าสุด; สิทธิ์ลงมติรายบุคคลยังไม่แจ้ง
