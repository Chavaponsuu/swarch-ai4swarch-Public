# รีวิวเบื้องต้นของร่าง ADR หลังผสานข้อเสนอที่ผู้ใช้ส่งมา

ประเมิน `exercise/outputs/2b-adr.md` ฉบับที่มี Recommendation เห็นด้วยกับทางเลือก 3 และผลกลุ่มยังเป็น `Pending Group Review` เป็นรีวิวของร่างที่ AI ช่วยเรียบเรียง ไม่ใช่การรีวิวหรืออนุมัติ ADR ฉบับสุดท้ายที่นักศึกษาเขียน และไม่ใช่มติจากคณะ review board

อ้างอิงย่อ: **ADR** = `exercise/outputs/2b-adr.md`; **S** = `docs/scenario.md` ใช้เฉพาะสองไฟล์นี้เป็นหลักฐาน; เลขบรรทัด S อ้างตามต้นฉบับภาษาอังกฤษ

## Quality-attribute scenarios

แต่ละข้อเรียงตาม แหล่ง · สิ่งกระตุ้น · สภาพแวดล้อม · การตอบสนอง · เกณฑ์วัด

1. **latency:** ลูกค้า · ส่ง 200 คำสั่งซื้อ/วินาที · พีค 11.11 ขณะ MailFast มี p95 1.5 s, p99 8 s และผิดพลาดประมาณ 0.5% · checkout เก็บ intent/order/outbox แล้วตอบโดยไม่รออีเมล · p95 ของ request รวมการเขียน store ≤ 500 ms และส่งอีเมลรวม retry ≤ 50/วินาที (S:24–26; ADR:Decision ข้อ 1–3, Validation)
2. **ความถูกต้องและเวลาแต้ม:** ผู้เรียกและระบบส่งข้อความ · retry key เดิมหลังคำตอบหาย และส่ง event ซ้ำหลัง ledger commit ก่อน ACK · โหลดพีค · คืน order/ผลแต้มเดิม · หนึ่ง order ต่อ request key ที่ถูกต้อง แต้มครั้งเดียวต่อ order และเวลาจาก commit `PLACED` ถึง commit แต้มรวม relay/คิว/retry ≤ 60 s โดยจุดเริ่มยังรอธุรกิจรับรอง (S:25,27; ADR:Decision ข้อ 1,3–4)
3. **availability:** loyalty · ล่ม 120 s ตามชุดทดลองที่เสนอ · order store ยังพร้อมและมีพื้นที่ · รับ order เก็บงานและตามให้แต้มหลังฟื้นตัว · ไม่มี order ล้มเหลวเพราะ loyalty และนับแต้มที่เกิน 60 s เป็น SLA breach เดิม; 120 s เป็น **Assumption** ของชุดทดลอง (S:27–28; ADR:Decision ข้อ 4, Validation)

|---|---|---|
| Non-risk | **[Inferred]** intent ก่อนผลภายนอก, request key คงเดิม และ ledger transaction ก่อน ACK เป็นมาตรการที่สอดคล้องกัน (ADR:Decision ข้อ 1–3) | ครอบคลุม request ซ้ำและ event ซ้ำคนละช่วง โดยไม่อ้างว่า RabbitMQ ให้ผลธุรกิจ exactly once เอง; ยังต้องพิสูจน์ด้วย validation |
| Risk | มีขั้นตอน/บทบาท reconciliation แต่ API ค้นผลและกันซ้ำของ payment/shipping รวมถึงผู้รับผิดชอบจริงยังไม่ยืนยัน (ADR:Decision ข้อ 2; Open questions) | เมื่อชำระเงินแล้วแต่บันทึกผลไม่ได้ เคสอาจค้างก่อนสร้าง event; ยังไม่มีหลักฐานว่าค้นผลและปิดเคสได้จริงโดยไม่ทำซ้ำ |

| Trade-off point | รับ order ต่อเมื่อ loyalty ล่ม ช่วย availability แต่แต้มบางรายการจะเกินกำหนดเมื่อ outage ยาว ซึ่งร่างเปิดเผยแล้ว (ADR:Decision ข้อ 4,6) | การเก็บงานไม่สูญหายไม่เท่ากับให้แต้มทันเวลา ยังอ้างว่าผ่าน S:27–28 ทุกกรณีไม่ได้จนมีข้อสรุปธุรกิจที่ชัดเจน |

## Missing or weak

- **ทางเลือกและผลกระทบ:** ทางเลือก 2 แยก worker/retry แล้ว จึงเป็นคู่เทียบที่เหมาะสม แต่ยังไม่มีข้อมูลภาระดูแล/กู้คืนสนับสนุนว่าทางเลือก 3 คุ้มกับ broker และ stores เพิ่มสำหรับทีม 4 คน (ADR:Considered options; Consequences; S:29–30)
- **หลักฐาน:** API ภายนอกและผลทดสอบระบบจริง: **Not evidenced in the provided files** งบเวลา 5/45/10 s และตัวอย่างพีคระบุเป็น **Assumption** แล้ว สำหรับงานเอกสารออกแบบคงเป็นแผน validation ได้ แต่ไม่ใช้ผลคำนวณแทนผลระบบจริง (ADR:Decision ข้อ 2,4–5; Validation)
- **สถานะการตัดสินใจ:** Recommendation ว่าเห็นด้วยไม่ใช่มติกลุ่ม Decision Record ยังคง Pending/TBD อย่างสอดคล้องกัน แต่จุดเริ่ม SLA, ข้อยกเว้นเมื่อ outage, รายชื่อผู้รับผิดชอบ และข้อมูลความจุยังรอข้อสรุปจริง (ADR:ข้อมูลสถานะ; Decision ข้อ 6; Open questions)

## Verdict

**accept with changes — สำหรับร่างเบื้องต้นเพื่ออภิปราย** เหตุผล ทางเลือก ข้อเสนอและแผน validation พร้อมให้กลุ่มพิจารณา แต่ยังไม่ยืนยันว่าระบบผ่านข้อกำหนดทั้งหมด ต้องปิดสามเรื่องนี้:

1. บันทึกมติจริงเรื่องนิยามเวลา order และข้อขัดแย้งเมื่อ outage เกิน 60 s พร้อมผู้ตัดสิน/วันที่; ก่อนมีมติคงนับกรณีล่าช้าว่าไม่ผ่าน SLA เดิม (S:27–28; ADR:Decision ข้อ 4,6)
2. ระบุผู้รับผิดชอบและหลักฐานวิธีค้นผล/กันซ้ำของ payment/shipping สำหรับ reconciliation หากยังไม่มีข้อมูลให้เปิดเผยข้อจำกัดไว้ ไม่เติมว่าบริการรองรับเอง (ADR:Decision ข้อ 2)
3. ให้กลุ่มรับรองหรือแก้สมมติฐานพีค/โหลดหลังพีคและแผน validation พร้อมประเมินภาระดูแลเทียบทางเลือก 2; แยกการรับแผนออกแบบออกจากการมีผลทดสอบยืนยัน (S:24–30; ADR:Validation)
