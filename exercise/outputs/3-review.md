# ADR-0002 Review

หลักฐาน: `docs/adr/0002-use-rabbitmq-for-post-order-actions.md` (ย่อ **ADR**) และ `docs/scenario.md` (ย่อ **Scenario**) เท่านั้น

## Quality-attribute scenarios

1. **Performance** — แหล่งกระตุ้น: ลูกค้า · สิ่งกระตุ้น: 200 orders/s · สภาพแวดล้อม: พีค 11.11, MailFast p95 1.5 s/p99 8 s · การตอบสนอง: เก็บ order/outbox แล้วแยกส่งอีเมล · ตัววัด: `PlaceOrder` p95 ≤ 500 ms รวมการเขียนใหม่; ส่งอีเมลรวม retry ≤ 50/s (Scenario:24–26; ADR:60–64,136)
2. **Correctness / timeliness** — แหล่งกระตุ้น: relay/consumer · สิ่งกระตุ้น: event ซ้ำหรือ crash หลัง ledger commit ก่อน ACK · สภาพแวดล้อม: โหลดพีคและเส้นทางแต้มพร้อม · การตอบสนอง: คืนผลเดิม ไม่เพิ่มแต้มซ้ำ · ตัววัด: ทุก order ได้แต้มครั้งเดียวภายใน 60 s จากเวลา “สั่งซื้อ” ที่ธุรกิจรับรอง รวมงานค้างเมื่อครบกำหนด (Scenario:25,27; ADR:65,79,137–138)
3. **Availability** — แหล่งกระตุ้น: บริการหลังสั่งซื้อ · สิ่งกระตุ้น: หยุดทำงาน รวมกรณี loyalty ล่ม > 60 s · สภาพแวดล้อม: order store พร้อมและมีพื้นที่ · การตอบสนอง: รับ order ต่อ เก็บงานและทำต่อเมื่อฟื้นตัว · ตัววัด: order ล้มเหลวเพราะบริการเหล่านี้ 0 รายการ; แต้มช้าต้องนับ SLA breach (Scenario:27–28; ADR:81,140)

## Findings table

| Type | Finding | Why it matters |
|---|---|---|
| Risk | รับ order ต่อเมื่อ loyalty ล่ม > 60 s ย่อมมีแต้มผิดกำหนด; ADR ยอมรับแต่ยังไม่มีมติแก้ (ADR:79–81,146) | รับรอง availability และ timeliness ตาม Scenario:27–28 พร้อมกันไม่ได้ในกรณีนี้ |
| Non-risk | คิวแยกตาม action และ ledger transaction กันซ้ำก่อน ACK สอดคล้องกับเป้าหมาย; ไม่อ้างว่า broker ให้ผลธุรกิจครั้งเดียวเอง (ADR:63–65) | แยกความล้มเหลวและป้องกันแต้มซ้ำตาม Scenario:27–28 ได้ในระดับข้อเสนอ; ยังต้องทดสอบ |
| Sensitivity point | ถ้าหนึ่งอีเมล/order งานค้างเพิ่มอย่างน้อย 150/s ระหว่างพีคก่อน retry; ไม่ทราบระยะพีค/อัตราหลังพีค (Scenario:25–26; ADR:26,83) | ยังระบุพื้นที่และเวลาระบายไม่ได้; เพิ่ม worker ไม่เพิ่มโควตา MailFast |
| Trade-off point | เพิ่ม RabbitMQ จาก PostgreSQL เพื่อกระจาย event และเพิ่ม action แลกกับระบบที่ต้องดูแลเพิ่ม (ADR:42,52,56) | modifiability แลก operability/cost ของทีม 4 คน; ประสบการณ์ RabbitMQ 2 คนยังไม่พิสูจน์ว่าดูแลไหว (Scenario:14,29–30; ADR:141,151) |

## Missing or weak

- **ทางเลือก:** มีสามแบบแล้ว แต่ควรเทียบ PostgreSQL job store แบบ event กลางพร้อมทะเบียนผู้รับด้วย **[Inferred]**; ข้อเสียเรื่องเพิ่ม action แล้วกระทบการสร้างงานใน ADR:51 ไม่จำเป็นต้องเกิดกับทุกแบบ
- **ผลกระทบ:** ADR ระบุความเสี่ยงพื้นที่เต็มและผล payment/shipping ก่อน commit แล้ว แต่ยังไม่ยืนยัน API ตรวจผล เจ้าของ reconciliation ระยะ outage ที่รองรับ อายุอีเมลที่ยอมรับ และแผนกู้คืน จึงยังปิดความเสี่ยง order ค้าง/งานล้นไม่ได้ (ADR:68–77,127,145–151)
- **หลักฐาน:** Validation ยังไม่รัน (ADR:9,132); UUID/store ปัจจุบันที่อ้าง source ใน ADR:28,60 ตรวจไม่ได้จากสองไฟล์นี้: **Not evidenced in the provided files** ส่วน Scenario:18 ยืนยันได้เฉพาะลำดับ synchronous และพฤติกรรมเมื่ออีเมลล้มเหลว

## Verdict

**accept with changes — ยอมรับแนวทางโดยมีเงื่อนไขสามข้อก่อนใช้งานจริง:**

1. ให้ธุรกิจรับรองจุดเริ่มนับ 60 s และนโยบายเมื่อ loyalty ล่มนาน โดยคงรายงาน breach จนกว่าจะเปลี่ยนข้อกำหนดชัดเจน (ADR:79–81,146)
2. เติมตัวเลขพีค/outage/เวลาระบายเป้าหมาย แผนพื้นที่และกู้คืน พร้อมเจ้าของ stores, broker และ reconciliation แล้วเทียบภาระกับทางเลือก 2 (ADR:141,145–151)
3. บันทึกผลทดสอบ 200 orders/s รวม crash/ข้อความซ้ำ/ผลภายนอกไม่แน่นอน เพื่อยืนยัน latency การไม่ให้แต้มซ้ำ และการกู้คืนงาน; Accepted ยังไม่ใช่หลักฐานว่าผ่าน (ADR:116,119,136–141)
