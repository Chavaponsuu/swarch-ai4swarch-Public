# ADR-0002: ใช้ event เพื่อแยกงานหลังการสั่งซื้อ

- **Status:** Proposed
- **Date:** 2026-10-27
- **Deciders:** ยังไม่ระบุผู้มีอำนาจตัดสินใจ ต้องยืนยันก่อนรับรอง ADR

## Context and problem

ใช้ requirement จากผู้ใช้เป็นหลักฐานด้านระบบเพียงแหล่งเดียว และใช้ `docs/adr/template.md` เป็นโครงสร้างเอกสาร:

| แหล่งอ้างอิง | ข้อเท็จจริงจาก requirement |
|---|---|
| requirement ข้อ 1 | หลังวางคำสั่งซื้อ Online Boutique ต้องส่งอีเมลยืนยันผ่าน MailFast ซึ่งเป็นผู้ให้บริการภายนอก และแทนที่ตรรกะจำลองของ `emailservice` |
| requirement ข้อ 2 | ต้องให้คะแนนสะสมผ่าน `loyaltyservice` ซึ่งยังต้องสร้างขึ้น |
| requirement ข้อ 3 | ต้องบันทึก analytics event ว่าเกิดการวางคำสั่งซื้อให้ทีมการตลาด |
| requirement ย่อหน้าสุดท้าย | ทีมการตลาดคาดว่าจะเพิ่ม SMS, fraud scoring และการอัปเดต recommendations ในปีถัดไป |

ต้องตัดสินใจว่างานเหล่านี้จะเชื่อมกับการวางคำสั่งซื้ออย่างไร เพื่อรองรับการเพิ่มงานและจัดการความล้มเหลวของแต่ละปลายทาง ไม่ทราบ call graph, protocol, data store, message broker, ปริมาณงาน หรือความสามารถ API ของ MailFast: **Not evidenced in the provided files**

ข้อเสนอและผลกระทบต่อไปนี้เป็น **[Inferred]** จาก requirement ไม่ใช่ข้อเท็จจริงเกี่ยวกับ implementation ปัจจุบัน และยังไม่ถือว่าผู้ใช้ยอมรับ eventual consistency หรือกำหนด SLA แล้ว

## Decision drivers

ลำดับความสำคัญที่เสนอ **[Inferred]** ซึ่งผู้ตัดสินใจต้องยืนยัน:

1. **Modifiability:** เพิ่มงานหลังสั่งซื้อได้โดยลดการแก้ส่วนที่ยืนยันคำสั่งซื้อ (requirement ย่อหน้าสุดท้าย)
2. **Reliability / correctness:** ทำงานทั้งสามให้ครบ และควบคุมผลซ้ำเมื่อ retry (requirement ข้อ 1–3; วิธีรับประกันเป็นข้อเสนอ)
3. **Availability / performance:** ลดผลของปลายทางที่ช้าหรือล่มต่อการวางคำสั่งซื้อ (ข้อเสนอจากการมีหลายปลายทาง)
4. **Operability / cost:** ติดตามงานค้างและความล้มเหลวได้ โดยคำนึงถึงต้นทุนและภาระดูแลที่ยังไม่ทราบ

## Considered options

1. ให้ตัวประสานงานเรียก MailFast, `loyaltyservice` และปลายทาง analytics แบบ synchronous หลังยืนยันคำสั่งซื้อ และเพิ่มการเรียกเมื่อมีงานใหม่
2. เผยแพร่ `OrderPlaced` แบบทนทาน แล้วให้ consumer ของแต่ละงานประมวลผลแบบ asynchronous ผ่าน message broker

### Pros and cons of the options

ผลเปรียบเทียบทั้งหมดเป็น **[Inferred]** จากรูปแบบที่เสนอ:

| Option | Pros | Cons |
|---|---|---|
| 1 — เรียกแบบ synchronous | ควบคุมและติดตามลำดับการเรียกได้ตรงไปตรงมา; รับรู้ผลการเรียกทันที; ไม่เพิ่ม broker จึงลดองค์ประกอบที่ต้องดูแล (operability / cost) | เวลาตอบกลับขึ้นกับปลายทางและ timeout (performance); เพิ่มงานต้องแก้ตัวประสานงาน (modifiability); ความล้มเหลวบางส่วนยังต้องมีสถานะถาวรและ retry โดยไม่ให้ผลซ้ำ และย้อนอีเมลที่ส่งแล้วไม่ได้ (reliability / correctness) |
| 2 — แยก consumer ผ่าน event | เพิ่ม consumer โดยลดการแก้ผู้เผยแพร่เมื่อ contract มีข้อมูลเพียงพอ (modifiability); แยก retry และขยายกำลังประมวลผลแต่ละงานได้ (availability / scalability); ไม่รอผลทุกปลายทางก่อนตอบผู้ใช้ (performance) | ผลลัพธ์เกิดตามหลังและอาจสำเร็จเพียงบางงาน (consistency); เพิ่ม broker และภาระดูแลสถานะกับการเฝ้าระวัง (cost / operability); ต้องจัดการ event สูญหาย ส่งซ้ำ และ schema เปลี่ยนแปลง (reliability / maintainability) |

## Decision

เสนอเลือก **ตัวเลือก 2** เพราะรองรับการเพิ่มงานตาม requirement ย่อหน้าสุดท้าย โดยให้ผู้ตัดสินใจยืนยันว่าการทำงานตามหลังการวางคำสั่งซื้อเป็นที่ยอมรับได้ รายละเอียดทั้งหมดในส่วนนี้เป็น **[Inferred]**:

- กำหนดจุดที่คำสั่งซื้อถือว่าวางสำเร็จ แล้วสร้าง `OrderPlaced` ณ ขอบเขตนั้น งานหลังสั่งซื้อไม่เป็นเงื่อนไขรอผลก่อนตอบว่าคำสั่งซื้อสำเร็จ
- ป้องกันช่องว่างระหว่างการยืนยันคำสั่งซื้อกับการเผยแพร่ event ด้วย transactional outbox หากขอบเขต transaction ของที่เก็บคำสั่งซื้อรองรับ หรือกลไกถาวรที่กู้คืนการเผยแพร่ได้เทียบเท่า ต้องออกแบบขอบเขตนี้ก่อนใช้จริง เพราะยังไม่ทราบวิธีเก็บคำสั่งซื้อ การบันทึกและ publish แยกกันโดยไม่มีวิธีกู้คืนไม่เพียงพอ
- ใช้ broker ที่เก็บข้อความแบบทนทานและมี subscription แยกสำหรับแต่ละงาน เพื่อให้ consumer ของอีเมล คะแนน และ analytics รับ event ได้ครบ โดยไม่แย่งข้อความระหว่างงาน ยังไม่เลือกผลิตภัณฑ์หรือ protocol
- เปลี่ยน `emailservice` เป็น consumer และ adapter ที่เรียก MailFast จริงแทนตรรกะจำลอง (เป้าหมายตาม requirement ข้อ 1; รูปแบบ consumer เป็นข้อเสนอ)
- สร้าง `loyaltyservice` เพื่อรับ event และบันทึกคะแนนตามกฎที่จะยืนยัน พร้อมป้องกันการให้คะแนนซ้ำ (requirement ข้อ 2)
- เพิ่ม consumer ที่บันทึกเหตุการณ์วางคำสั่งซื้อไปยังปลายทาง analytics ที่ทีมการตลาดจะยืนยัน (requirement ข้อ 3) การ publish event ภายในอย่างเดียวยังไม่นับว่างานบันทึก analytics สำเร็จ
- เสนอ event contract ที่มี `event_id`, `order_id`, `occurred_at` และ `schema_version` พร้อมข้อมูลอ้างอิงที่แต่ละงานต้องใช้ ต้องตกลงวิธีเข้าถึงข้อมูลเพิ่มเติมและจำกัดข้อมูลส่วนบุคคลก่อนใช้จริง โดยไม่ถือว่ามี field เหล่านี้ในระบบเดิม
- ออกแบบสำหรับ at-least-once delivery: consumer เก็บสถานะสำเร็จถาวรและป้องกันผลซ้ำตาม `order_id` กับชนิดงาน การให้คะแนนและ analytics ต้องบันทึกผลกับสถานะป้องกันซ้ำอย่างสอดคล้องกัน ไม่อาศัยเพียงการจำ `event_id` หากหลาย event อาจแทนคำสั่งซื้อเดียวกัน
- สำหรับ MailFast ให้ใช้ idempotency key คงเดิมต่ออีเมลหนึ่งรายการหาก API รองรับ หาก timeout หลังผู้ให้บริการอาจรับคำขอแล้ว ให้ตรวจสอบสถานะหรือกระทบยอดก่อน retry เมื่อทำได้ ยังรับประกันการส่งเพียงครั้งเดียวไม่ได้หาก API ไม่มีความสามารถที่จำเป็น
- แยก retry ของแต่ละงานด้วย backoff และส่งงานที่เกินนโยบาย retry ไป dead-letter queue พร้อมแจ้งเตือนและขั้นตอน replay ที่ยังป้องกันผลซ้ำ กำหนดจำนวนครั้ง ระยะเวลา และการเก็บรักษาหลังทราบข้อจำกัดจริง
- เพิ่ม SMS และ recommendations ด้วย consumer ใหม่เมื่อ contract เพียงพอ ส่วน fraud scoring ต้องยืนยันว่าผลจำเป็นก่อนอนุมัติคำสั่งซื้อหรือไม่ หากจำเป็น จะต้องมีการตัดสินใจแยกจากงานหลังสั่งซื้อใน ADR นี้

## Consequences

ผลกระทบต่อไปนี้เป็น **[Inferred]** จากการตัดสินใจที่เสนอ:

- **Positive:** เพิ่มและปรับใช้ consumer แยกกันได้เมื่อ event contract รองรับข้อมูลที่ต้องการ (quality attribute: modifiability)
- **Positive:** ความขัดข้องของปลายทางหนึ่งไม่บังคับให้งานอื่นหยุด และงานค้างกลับมาทำต่อได้ภายในความจุและนโยบายเก็บรักษาที่กำหนด (quality attribute: availability / reliability)
- **Positive:** เส้นทางตอบกลับการวางคำสั่งซื้อไม่รอผลจากทุกปลายทาง แต่ยังมีต้นทุนการบันทึกข้อมูลเพื่อเผยแพร่ event อย่างทนทาน (quality attribute: performance)
- **Negative:** อีเมล คะแนน และ analytics อาจเสร็จต่างเวลากันหรือค้างบางงาน ต้องตกลงเวลาที่ยอมรับได้และวิธีแสดงสถานะ (quality attribute: consistency / usability)
- **Negative:** เพิ่มค่าใช้จ่ายและภาระดูแล broker, กลไกเผยแพร่, consumer, dead-letter queue และข้อมูลติดตาม (quality attribute: cost / operability)
- **Risks and mitigations:** คำสั่งซื้อสำเร็จแต่ event หาย ให้ป้องกันด้วยกลไกเผยแพร่ที่กู้คืนได้และกระทบยอดคำสั่งซื้อกับงานที่ควรเกิด (quality attribute: reliability)
- **Risks and mitigations:** ผลซ้ำจาก retry ให้ใช้การป้องกันซ้ำถาวรและกระทบยอดปลายทาง โดยยอมรับข้อจำกัดที่ยังไม่ทราบของ MailFast (quality attribute: correctness)
- **Risks and mitigations:** backlog, schema ที่เข้ากันไม่ได้ และข้อมูลส่วนบุคคลใน event ให้ติดตามอายุงานค้าง ใช้ schema version ที่เข้ากันได้ จำกัดข้อมูลและสิทธิ์เข้าถึง พร้อมกำหนดการเก็บรักษา (quality attribute: performance / maintainability / security / privacy)

## Validation

แผนตรวจสอบที่เสนอ **[Inferred]**; เป้าหมายเชิงตัวเลขและวันทบทวนยังต้องตกลง:

- ทดสอบจากคำสั่งซื้อสำเร็จจนมีหลักฐานแยกกันว่า MailFast รับคำขอส่งอีเมล คะแนนถูกบันทึกตามกฎ และ analytics บันทึกเหตุการณ์แล้ว การรับคำขอของ MailFast ไม่ยืนยันว่าอีเมลถึงกล่องผู้รับ ต้องตกลงนิยามความสำเร็จและวิธีติดตาม
- จำลอง crash ระหว่างยืนยันคำสั่งซื้อกับ publish และระหว่าง consumer ทำผลข้างเคียงกับบันทึกสถานะสำเร็จ ตรวจว่างานกู้คืนได้และคะแนนหรือ analytics ไม่เกิดผลซ้ำ ตรวจผลอีเมลตามความสามารถ API ที่ยืนยันแล้ว
- ส่ง event ซ้ำและ replay จาก dead-letter queue ตรวจว่าการป้องกันผลซ้ำใช้ได้ตลอดช่วง retry และ replay ที่ตกลงกัน
- จำลอง MailFast, loyalty, analytics และ broker ไม่พร้อมใช้งานแยกกัน ตรวจว่างานไม่หาย งานอื่นเดินต่อได้ตามที่ออกแบบ และระบบฟื้นตัวได้ กำหนดพฤติกรรมเมื่อพื้นที่เก็บงานค้างเต็มก่อนรับรอง
- ทดสอบด้วยปริมาณงานที่ยืนยันภายหลัง วัด latency ของการวางคำสั่งซื้อ อายุงานค้าง อัตราสำเร็จ เวลาไปถึงผลลัพธ์ของแต่ละงาน retry และ dead-letter queue แล้วเทียบกับเป้าหมายที่ตกลง
- ทดลองเพิ่ม consumer โดยไม่แก้ผู้เผยแพร่เมื่อ contract เพียงพอ และทดสอบความเข้ากันได้ของ schema ต่างรุ่น

## Open questions

ข้อมูลต่อไปนี้ยังไม่ปรากฏในหลักฐานที่อนุญาต (**Not evidenced in the provided files**):

- ใครเป็นผู้ตัดสินใจ และยอมรับ eventual consistency สำหรับอีเมล คะแนน และ analytics ได้หรือไม่? แต่ละงานต้องเสร็จภายในเท่าไร และทบทวน ADR เมื่อใด?
- คำสั่งซื้อถือว่าสำเร็จที่จุดใด เก็บที่ใด และรองรับ transaction แบบใด? จะรักษาความสอดคล้องระหว่างคำสั่งซื้อกับ event และรับมือ broker หยุดทำงานหรือพื้นที่เต็มอย่างไร?
- ปริมาณคำสั่งซื้อ ช่วงโหลดสูงสุด งบประมาณ ความสามารถของทีม และระบบ messaging ที่มีอยู่คืออะไร?
- MailFast มี API, authentication, rate limit, idempotency, สถานะการส่ง และวิธีกระทบยอดอะไรบ้าง? นิยามความสำเร็จของการส่งอีเมลคืออะไร?
- คำนวณคะแนนอย่างไร ระบุตัวสมาชิกจากข้อมูลใด และมีนโยบายเรื่องคำสั่งซื้อยกเลิกหรือคืนเงินอย่างไร?
- ปลายทางและ schema ของ analytics คืออะไร? ต้องป้องกัน event ซ้ำและเก็บข้อมูลไว้นานเท่าใด?
- consumer ต้องใช้ข้อมูลใด จะส่งใน event หรืออ่านเพิ่มเติมอย่างไร และมีข้อกำหนดด้านความเป็นส่วนตัว สิทธิ์เข้าถึง และการเก็บรักษาอย่างไร?
- ใครรับผิดชอบ retry, dead-letter queue, replay และการกระทบยอด? ต้องเก็บสถานะป้องกันซ้ำนานเท่าใด?
- fraud scoring ในอนาคตเป็นงานหลังสั่งซื้อ หรือเป็นเงื่อนไขอนุมัติก่อนยืนยันคำสั่งซื้อ?
